# NIM vs vLLM — Observability: Traces & Metrics

## NeMo Agent Toolkit (NAT)

NAT is NVIDIA's framework for building agentic AI workflows. It orchestrates LLMs, tools, embedders, and guardrails via a YAML config. The `llms` block in `config.yml` defines which inference backend NAT calls:

| `_type` | Backend | Notes |
|---|---|---|
| `nim` | NVIDIA NIM container | NIM-specific auth/retry defaults |
| `openai` | Any OpenAI-compatible endpoint | Self-hosted vLLM (no auth required) or cloud APIs (OpenAI, Groq, etc.) with `api_key` |
| `aws_bedrock` | AWS Bedrock | — |

Example (NIM self-hosted — Docker or K8s, `base_url` points to container host):
```yaml
llms:
  nim_llm:
    _type: nim
    model_name: meta/llama-4-scout-17b-16e-instruct
    base_url: "http://localhost:8001/v1"      # Docker: localhost; K8s: http://<nim-service>:8001/v1
    temperature: 0.1
```

When `base_url` is omitted, NAT defaults to NVIDIA's hosted API (`integrate.api.nvidia.com`) on. The `api_key` field is also valid for self-hosted NIM endpoints that require authentication.  Refer to [NVIDIA Build](https://build.nvidia.com).

```yaml
llms:
  nim_llm:
    _type: nim
    model_name: google/gemma-4-31b-it
    api_key: "${NVIDIA_API_KEY}"
    temperature: 0.1
```

Example (bare vLLM self-hosted — Docker or K8s):
```yaml
llms:
  my_llm:
    _type: openai
    base_url: "http://localhost:8000/v1"      # Docker: localhost; K8s: http://<vllm-service>:8000/v1
    model_name: meta-llama/Llama-3.1-8B-Instruct
    # api_key: "${MY_API_KEY}"               # omit for self-hosted; required for cloud endpoints
```

## Key Fact: NIM is Not the Same as vLLM

NIM is NVIDIA's packaged container that wraps an inference backend (vLLM or TensorRT-LLM depending on GPU/model). vLLM is the open-source inference engine that runs the model directly.

## Distributed Tracing (OpenTelemetry)

Both NIM and bare vLLM support OTel tracing — it is **not** a NIM-exclusive feature.

**How NIM traces work:**
- NIM forwards the W3C `traceparent` header to its inference backend
- Spans are generated by the backend (vLLM), not NIM itself
- Enabled via env var on the NIM pod: `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`

**How bare vLLM traces work (same env vars):**
```yaml
env:
  - name: OTEL_EXPORTER_OTLP_TRACES_ENDPOINT
    value: "http://<otel-collector>:4318/v1/traces"
  - name: OTEL_EXPORTER_OTLP_TRACES_PROTOCOL
    value: "http/protobuf"      # or grpc → port 4317
  - name: OTEL_SERVICE_NAME
    value: "vllm-inference"
```

vLLM emits **2 spans per request**: one for the client prompt, one with inference metadata. It supports W3C `traceparent` propagation via `TraceContextTextMapPropagator`.

**Layer diagram (NIM path — `_type: nim`):**
```
┌─────────────────────────────────────────┐
│  NAT Workflow                           │  ← spans emitted here (agent, tool, LLM steps)
│  react_agent, tools, guardrails         │
└────────────┬────────────────────────────┘
             │ HTTP POST /v1/chat/completions
             │ + W3C traceparent header propagated
             │ + NVIDIA-specific headers (X-Request-Id, etc.)
┌────────────▼────────────────────────────┐
│  NIM container                          │  ← NVIDIA packaging layer
│  auth, health, model routing            │    forwards traceparent to backend
└────────────┬────────────────────────────┘
             │ internal dispatch
      ┌──────┴──────┐
      ▼             ▼
┌──────────┐  ┌──────────────┐
│  vLLM    │  │ TensorRT-LLM │  ← NIM picks based on GPU/model
└────┬─────┘  └──────┬───────┘    spans emitted here (2 per request)
     └────────┬──────┘
              ▼
┌─────────────────────────────────────────┐
│  GPU (CUDA kernels)                     │
└─────────────────────────────────────────┘
```

**Layer diagram (bare vLLM path — `_type: openai`):**
```
┌─────────────────────────────────────────┐
│  NAT Workflow                           │  ← spans emitted here (agent, tool, LLM steps)
│  react_agent, tools, guardrails         │
└────────────┬────────────────────────────┘
             │ HTTP POST /v1/chat/completions
             │ + W3C traceparent header propagated
┌────────────▼────────────────────────────┐
│  vLLM                                   │  ← spans emitted here (2 per request)
└────────────┬────────────────────────────┘
             ▼
┌─────────────────────────────────────────┐
│  GPU (CUDA kernels)                     │
└─────────────────────────────────────────┘
```

**NAT workflow traces** (agent steps, tool calls, token counts) are a **separate** trace source configured in `config.yml` under `general.telemetry`. They stitch with vLLM/NIM inference spans via the shared `traceparent` header.

## NAT Workflow Span Attributes

NAT's observability layer is **provider-agnostic** — the same span attributes are emitted whether `_type: nim` or `_type: openai` is configured:

| Attribute | Description |
|---|---|
| `nat.span.kind` | `LLM`, `TOOL`, `AGENT`, `GUARDRAIL`, `EMBEDDER`, etc. |
| `input.value` / `input.mime_type` | Prompt text or JSON |
| `output.value` / `output.mime_type` | Response text or JSON |
| `llm.token_count.prompt/completion/total` | Per-call token counts |
| `nat.usage.num_llm_calls` | LLM calls in workflow |
| `nat.usage.seconds_between_calls` | Latency between calls |
| `nat.usage.token_count.*` | Aggregate workflow token counts |
| `nat.metadata` | Serialized step metadata |

Note: no `llm.provider` or `llm.model_name` attribute is written by NAT — provider type is not recorded in traces.

## Prometheus Metrics

**NIM and vLLM expose identical metrics.**

From the official NIM docs:
> *"NIM passes through the inference backend's native Prometheus metrics without modification. The metrics available at `/v1/metrics` are the same metrics produced by vLLM."*

Scrape endpoint (both): `http://<host>:8000/v1/metrics`

Metrics include: request latency, throughput, queue depth, token counts, GPU utilization.
